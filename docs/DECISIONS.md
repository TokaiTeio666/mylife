## 1. 交付根目录与仓库形态

**影响**：PR 写到哪里、验收第 5 条在哪里验证、生成物是否会回流到证据池。

| 选项 | 做法 | 优点 | 代价/风险 |
|---|---|---|---|
| **A** | `managed` 独立输出仓库 + `wiki/复盘/...` | 对齐 FR-E9；不写用户源 Vault；生成物不回流；PR 可审 | 需为每个 Workspace 配一个输出仓库；Obsidian 需拉取/镜像该仓库 |
| **B** | 直接写回源 Vault + `wiki/复盘/...` | 用户在 Obsidian 立即看到；少一个仓库 | 需源仓库写权限；生成物进入源仓库，必须靠 `documents.source_type=generated` 排除；Obsidian Git 同步冲突风险高 |
| **C** | `managed` 仓库 + `data/reviews/...` | 严格对齐 REQUIREMENTS §6.3 的完整目录树；与源笔记彻底分离 | 与 FR-E9 的 `wiki/复盘` 冲突，需改需求；Obsidian 中不直观 |
| **D** | 每 Workspace 可配置，**默认 A** | 灵活，适配 SaaS 多租户；默认仍满足 FR-E9 | 多一个配置项；验收必须固定默认值 |

**推荐：D（默认 A）**。理由：MVP 要的是“不污染源 Vault + 对齐 FR-E9 + 可审 PR”，A 同时满足；保留配置是为了后续团队/多 Vault 场景，不增加 MVP 实现量。

**若选 A/D 的落地改动**：§8.1 保持现状；§14 路径冲突行标记“已裁决”；`git_connections.mode` 默认 `managed`；验收第 5 条在输出仓库的 `wiki/复盘/每日复盘/2026/2026-10-27.md` 验证。

## 2. Embedding 换模与维度

**影响**：`document_chunks.embedding` 的列维度、迁移方案、FR-G2 的验收口径。

| 选项 | 做法 | 优点 | 代价/风险 |
|---|---|---|---|
| **A** | 固定 BGE-M3 1024 维，首配后不可换 | 最简单；无迁移代码 | FR-G2“可配置维度”只能算部分满足；换模型需手工重建 |
| **B** | 首配可选模型/维度；换维走蓝绿迁移 | 满足 FR-G2；不阻塞请求路径；可回滚 | 需 `embedding_profiles` + 新表/新索引 + 全量 re-embed + 原子切换 |
| **C** | 在线热切换（双写双读） | 切换无停机 | 复杂度高；双份存储与一致性成本；MVP 不需要 |
| **D** | 外接向量数据库（Qdrant/Milvus） | 维度与索引更灵活；可独立扩容 | 新增运维组件，偏离 §8.1 的 pgvector 基线 |

**推荐：B**。理由：MVP 允许首配（默认 BGE-M3 1024 维），换维作为运维任务走蓝绿迁移；C 留给二期，D 不作为首版。

**若选 B 的落地改动**：§2.6 已写蓝绿流程；§6 已有 `embedding_profiles`；`workspace_settings.embedding_profile_id` 指向 active；验收增加“换维后旧索引可回滚”。

## 3. 日报自动合并

**影响**：PR 噪音、用户信任、交付层工作量。

| 选项 | 做法 | 优点 | 代价/风险 |
|---|---|---|---|
| **A** | 所有复盘都人工合并 PR | 最安全；用户完全掌控 | 每天一个 PR，噪音大；用户可能放弃审阅 |
| **B** | daily 可 opt-in auto-merge（Gate 全通过才合并）；monthly/yearly 人工 | 降低日常噪音；重要复盘仍人工 | 需要“信任开关”；auto-merge 出错需可回滚 |
| **C** | 所有类型 Gate 通过即 auto-merge | 最低摩擦 | 错误内容直接进入长期知识；信任风险最高 |
| **D** | daily 直推 `reviews` 分支不建 PR；monthly 汇总 PR | 日常零 PR；月报集中审 | daily 出错只能靠回滚；与“提 PR”的用户预期部分偏离 |

**推荐：B**。理由：daily 是高频低风险，适合 opt-in 自动；monthly/yearly 是聚合与长期结论，必须人工。

**若选 B 的落地改动**：§8.2 增加 `auto_merge` 策略；§16.3 `delivery-profile.yml` 已声明；§14.1 第 3 项标记为已裁决。

## 4. 专题页新增条目确认

**影响**：`错误清单/正确方法论/行动清单` 的长期可信度与维护摩擦。

| 选项 | 做法 | 优点 | 代价/风险 |
|---|---|---|---|
| **A** | 所有新增条目都人工确认 | 最高可信度 | 摩擦大；条目多时不可持续 |
| **B** | 首见条目人工确认；复发/完成回填自动 | 新知识有人把关；重复维护自动化 | 首见仍需人工窗口 |
| **C** | 全自动 + 审计 + 一键回滚 | 最低摩擦 | 错误条目可能进入长期知识，事后发现成本高 |
| **D** | 错误类人工确认；方法论/行动自动 | 风险分级 | 规则复杂；方法论错误同样危险 |

**推荐：B**。理由：与 LLM-Wiki 的“长期知识四道门”一致；新增是“进入长期库”的关键动作，复发/回填只是已有条目的状态更新。

**若选 B 的落地改动**：§7.3 已写；§16.4 门三已写；`topic_items.status` 的 `open → resolved` 只由显式回填/人工确认触发。

## 5. 预算数值

**影响**：成本上限、降级触发、用户体验。以下为**每次 run 的 token 上限（输入/输出）**，不是货币；实际费用按所选模型单价换算。

| 选项 | daily | monthly | yearly | 每 Workspace 月上限 | 适用 |
|---|---|---|---|---|---|
| **A 紧凑** | 50k / 10k | 150k / 30k | 500k / 100k | 2M / 400k | 早期验证、低预算 |
| **B 标准** | 100k / 20k | 300k / 60k | 1M / 200k | 5M / 1M | 推荐；覆盖 2–3 轮修订 |
| **C 宽松** | 200k / 40k | 600k / 120k | 2M / 400k | 10M / 2M | 长笔记、多轮返工 |
| **D 只告警** | 不硬停 | 不硬停 | 不硬停 | 阈值告警 | 不推荐；账单不可控 |

**推荐：B**，并在 80% 告警、100% 硬停；预算跨重试与修订累计，不允许每步重置。

**若选 B 的落地改动**：§9.4 的 per-role 预算乘以修订轮数即可覆盖；`budget-guard` 在每次 LLM 调用前检查；超限终止为 `FAILED/NEEDS_HUMAN`，不输出“数据版复盘”。

## 6. Reviewer 异构模型

**影响**：评审独立性、成本、供应商依赖。

| 选项 | 做法 | 优点 | 代价/风险 |
|---|---|---|---|
| **A** | 单 Reviewer（同族）+ 确定性门禁 | 成本低；确定性门禁才是 blocking，LLM 只 advisory | 同族模型可能共享盲区 |
| **B** | 双 Reviewer（同族、不同 prompt） | 比单评审多一层自洽检查 | 成本翻倍；同族盲区仍在 |
| **C** | 异构 Reviewer（不同 provider/model）用于 monthly/yearly | 独立性最好；适合高价值产物 | 需第二 provider 与密钥；接口兼容性风险 |
| **D** | monthly/yearly 只人工评审，不做 LLM Reviewer | 质量最高 | 人工成本高；自动化程度低 |

**推荐：A 作为 MVP；C 仅用于 monthly/yearly 作为 Phase 2 增强**。理由：FR-G1 只保证 OpenAI 兼容接口，不保证有第二个模型族；确定性门禁（G0–G9）已经承担 blocking，LLM judge 不应成为单点。

**若选 A 的落地改动**：§9.4 Reviewer 行保留“强（异族）”改为“强（同族）”；§14.1 第 6 项标记；Phase 2 再加 C。

## 7. 删除边界

**影响**：NFR-9/Q9 合规、Git 历史不可变性、用户告知。

| 选项 | 做法 | 优点 | 代价/风险 |
|---|---|---|---|
| **A** | 30 天冷却；清除 DB/MinIO/向量/凭据；Git 历史保留 | 符合 Q9；Git 不可变；可审计 | 已合并的 Git 历史仍可被仓库协作者看到，需明确告知 |
| **B** | 30 天冷却 + Git 历史重写（force push） | 表面“彻底删除” | 破坏协作历史；可能影响其他克隆；高风险 |
| **C** | 永久软删除（保留数据，仅隐藏） | 可恢复 | 不符合删除承诺；合规风险 |
| **D** | 7 天冷却 + 立即清理 Git | 响应快 | 误删难恢复；与 Q9 的 30 天冲突 |

**推荐：A**。理由：与已冻结的 Q9 一致；Git 作为交付与审计载体，不应被重写；删除前提供导出，删除后明确告知“已合并的 Git 历史无法从历史中抹除”。

**若选 A 的落地改动**：§14 删除边界行保留；`deletion_requests` 状态机 `requested → cooling → purged`；purge 任务覆盖 DB/MinIO/向量/凭据；用户协议与删除确认页写明 Git 历史边界。
